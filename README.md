## 一、产品定位
### 1.1 一句话定义
> **薯光 Lumi 是给内容生态观察者使用的判断力训练与沉淀工具。**

它不是笔记工具，不是知识库，不是 AI 聊天助手，也不是创作者灵感本。  
它做且只做一件事：**帮助以观察内容为职业的人，把无形的内容判断沉淀下来，并让这些判断随时间形成可见的专业能力图谱。**
### 1.2 产品命名
- **中文名**：薯光  
  命名逻辑："薯"来自小红书内部文化自称（薯厂、薯员工），对应核心目标用户群体；"光"取拉丁语 *lumen* 之意，意为"让你看见原本看不见的东西"——对应产品将无形判断变得可见的核心价值。
- **英文名**：Lumi  
  作为品牌在非中文语境下的延伸使用。

## 二、问题定义
### 2.1 核心问题
内容生态岗位的从业者（风控、运营、社区生态、投放研究等），每天都在产生大量内容判断：

- 某类笔记的评论区开始出现新型引流模式
- 某个品牌的投放策略在悄悄变化
- 某种情绪叙事方式正在批量复制

但这些判断绝大多数会消散。原因不是从业者不重视，而是：

1. **没有低门槛记录方式**：现有工具（飞书、Notion）要求在记录的那一刻就把东西整理清楚——打开文档要想文件夹、标题、分类——这个门槛在高强度内容审核的节奏下，让大多数人直接放弃。
2. **判断散落在个体脑中，无法沉淀和传承**：老员工离职后，三年积累的内容直觉随之带走；新员工只能重新踩坑。
### 2.2 薯光的竞争对手不是飞书
这一点非常重要。

薯光的竞争对手不是"功能更强大的笔记应用"，而是**"什么都不记"这个行为本身**。  
它服务的是那个"本来不会打开任何应用去记录"的时刻。

这也意味着：

> 如果一个人已经在认真使用飞书记录内容洞察，薯光对他的价值有限。  
> 薯光的目标用户，是那个在内容判断消散前最需要一个超低门槛出口的人。

***
## 三、目标用户
### 3.1 核心用户群
**以观察内容为职业的人**，而非泛化的"内容创作者"。

| 岗位 | 判断消散的场景 | 对薯光的需求 |
|------|--------------|------------|
| 内容风控 | 发现一种新型违规模式，但没有记下来，三个月后写报告全靠记忆 | 低门槛捕捉单次判断，AI 辅助结构化 |
| 内容运营 | 感觉某类内容的情绪浓度在上升，但无法向上游说清楚"我是怎么发现的" | 将直觉转化为可引用、可复述的结构化判断 |
| 社区生态 | 跟踪某个话题的走向，但判断散落在不同时间，缺少回看线索 | 建立时间轴式判断轨迹 |
| 投放研究 | 感知某个品牌的种草方式在变化，但说不清楚是从哪篇开始的 | 多条记录后形成"模式卡"，自动浮现共性 |
### 3.2 用户验证状态
当前核心用户假设**尚未经过真实用户测试验证**。  
基于真实小红书内容从业者的访谈（非正式）做出判断，样本量极小（n=1）。  
这是下一步必须验证的最重要假设。

## 四、产品逻辑
### 4.1 核心闭环
```
用户看到一条有意思的内容
        ↓
选择一个观察视角（我这次在用哪副眼镜？）
        ↓
写一句自己的判断
        ↓
AI 基于所选视角，辅助结构化这条判断
        ↓
技能经验积累 + 宠物成长
        ↓
同一视角下多条判断后 → 生成"模式卡"
        ↓
模式卡沉淀到 Observation Log 顶部
        ↓
用户看见自己正在形成的内容观察能力
```

**核心设计原则**：AI 不替用户判断，AI 帮用户整理判断。
### 4.2 五个观察视角
每次录入，用户先选择本次使用的观察视角：

| 视角 | 含义 | 对应技能 |
|------|------|--------|
| Comment signals / 评论区信号 | 正文之外，评论区发生了什么；是否有争议、引流、补充信息、真实用户反馈 | 评论区猎手 Comment Hunter |
| Emotional resonance / 情绪共鸣 | 这条内容激发了什么情绪；焦虑、认同、愤怒、安慰在哪里 | 情绪捕手 Emotion Catcher |
| Commercial traces / 商业痕迹 | 是否有软广、投放植入、转化链路；种草内容和真实分享的边界在哪 | 商业嗅觉 Commercial Instinct |
| Trend shift / 趋势变化 | 这类内容是否正在变多；标题、结构、叙事方式是否在模板化；平台生态出现新方向 | 趋势雷达 Trend Radar |
| Risk boundary / 风险边界 | 内容是否在擦边；有无引流、虚假宣传、灰产暗示；风险是否不在正文而藏在评论或私信链路 | 风险边界感 Risk Sensor |

**为什么视角要用户主动选，而不是 AI 自动判定**  
因为"用什么眼镜看内容"是一种职业意识，应该由用户主动决定。  
用户选视角的过程本身就是在训练内容判断框架。如果完全由 AI 判定，用户感知不到自己在往哪个方向积累。
### 4.3 AI 的角色定义
AI 在薯光中扮演**结构化助手**的角色，而非替代判断的智能系统：

- 基于用户选定的观察视角，对内容做聚焦摘要
- 将用户的一句话判断扩展为可引用、可沉淀的结构化表达
- 提取内容类型标签和洞察标签
- 计算技能经验，触发技能解锁
- 在同一视角累计足够多记录后，生成"模式卡"

**当前 Demo 实现方式**：AI 分析为预置逻辑（非实时 API 调用），使用 5 条真实小红书笔记数据。  
**未来真实版本**：接入 LLM API 实现任意内容的实时解析和结构化。

## 五、功能模块说明
### 5.1 Workspace（工作区）
**功能定位**：产品核心入口，完成一次完整的"判断捕捉与结构化"动作。

**录入流程**：
1. 粘贴内容链接（可选）
2. 填写内容标题（可选）
3. 粘贴正文内容（可选）
4. 选择观察视角（必选，五选一）
5. 填写一句话判断（必填）
6. 点击「Analyze with Lumi」

> 三个可选项里只要有一项有内容，加上视角选择和一句话判断，即可完成一次有效录入。  
> 预计完整录入时间：30 秒以内。

**分析结果区展示内容**（有序）：
1. 内容摘要
2. 所选观察视角
3. 基于视角的结构化判断
4. 洞察标签
5. 获得的技能经验值

**快捷功能**：  
「试试样例模板」按钮可随机加载一条预置的真实小红书笔记，供新用户快速体验完整流程。

***
### 5.2 宠物系统（Pet Companion）
**功能定位**：将职业判断力的积累，变成有情感温度的即时反馈机制。

**设计逻辑**：  
「维护知识库」是有心理负担的任务，但「喂宠物」没有。宠物把"记录判断"这个行为从任务变成日常，让低频、低动力的行为更容易持续。

**Onboarding 流程**：
1. 选择宠物形象（小猫 / 小狗 / 纸盒子 / 一瓶可乐）
2. 为宠物起名
3. 选择陪伴方式（专业型 / 亲近型）——影响产品全程的文案语气

**陪伴方式说明**：

| 陪伴方式 | 适合场景 | 语气风格示例 |
|---------|---------|------------|
| 专业型 | 风控、运营、研究等职业化场景 | "在 Comment signals 维度，你已形成稳定判断模式。" |
| 亲近型 | 更感性、更轻量的使用者 | "你最近真的很会从评论区闻出不对劲。" |

**经验成长逻辑**：  
每次完成观察录入，宠物在对应视角获得技能经验值（XP）。  
XP 积累到解锁门槛时，宠物习得对应技能称号。

***
### 5.3 五个技能（Skill System）
| 技能 | 对应视角 | 解锁描述 |
|------|---------|---------|
| 评论区猎手 Comment Hunter | Comment signals | 善于从评论区发现正文之外的真实信号 |
| 情绪捕手 Emotion Catcher | Emotional resonance | 能感知内容中的情绪驱动力 |
| 商业嗅觉 Commercial Instinct | Commercial traces | 能识别内容背后的品牌与变现逻辑 |
| 趋势雷达 Trend Radar | Trend shift | 能从碎片中捕捉内容生态的变化方向 |
| 风险边界感 Risk Sensor | Risk boundary | 能识别内容中潜在的平台风险信号 |

**技能设计原则**：  
技能描述的是"你习惯用什么视角看内容"，而不是"你看了什么品类的内容"。  
因此技能体系描述的是**人的能力特征**，不是内容品类标签。

***
### 5.4 模式卡（Pattern Card）
**功能定位**：将零散的单条判断，提升到"模式级洞察"。

**触发机制**：  
当某个视角下的记录数量达到触发门槛（当前 Demo 设定为 3 条），AI 自动生成一张模式卡。

**模式卡结构**：

| 元素 | 内容 | 说明 |
|------|------|------|
| 状态标签 | Pattern surfaced | 与普通记录区分 |
| 所属视角 | Comment signals | 对应五视角之一 |
| 模式名称 | 正文无害，评论区在做生意 | 一句能被记住的命名 |
| 一句说明 | 最近 4 条观察里你反复注意到…… | 控制在 2 行以内 |
| 证据引用 | 来自 2 条具体判断记录 | 最多 2 条，不超量 |
| 行动入口 | 查看相关记录 | 明确的单一动作 |

**模式卡的产品意义**：

> 飞书和 Notion 帮你存记录。薯光帮你把记录里的共性浮现出来，变成你能说出口的专业判断。  
> 这是薯光区别于所有现有笔记工具的核心差异点。

***
### 5.5 Observation Log（观察轨迹）
**功能定位**：你的判断成长时间轴，不是内容收藏夹。

**信息层级**（从高到低）：
1. 所选观察视角（最顶部）
2. 技能贡献标签
3. **用户的一句话判断**（视觉权重最大）
4. AI 结构化标签
5. 原始内容标题 / 摘要（作为背景证据）

顶部置顶区：最近生成的**模式卡**

**设计说明**：  
这个层级设计的意图是：Observation Log 存的是**你怎么看内容**，而不是**你看了什么内容**。  
用户的一句话判断是主角，原始内容只是证据。

***
### 5.6 Community（社区）
**当前阶段定位**：未来扩展模块，不是当前产品的核心价值载体。

**设计方向**：  
当多人都在积累观察能力后，形成基于技能标签的轻社区。  
板块按技能划分，习得对应技能才能进入，贴近"按能力分层的内部社区"逻辑。

**当前功能**：
- 技能排行榜（按技能总数、单技能熟练度）
- 技能板块入口（以最近的模式卡作为板块内容，避免空板块）
- 简单互动入口

**终面演示策略**：  
不将 Community 作为核心卖点。定位表述为：  
> "当团队多人使用时，可以在这里看到集体的技能分布，并围绕某个具体模式展开讨论。"

## 六、产品验收：已达标 / 待验证 / 已知局限
### 6.1 当前已达标项（Demo 级别）
- ✅ 问题定义清晰，有第一手用户观察作为基础
- ✅ 用户定义已收窄，避免"面向所有人"的陷阱
- ✅ 核心闭环完整可演示（录入 → 分析 → 宠物成长 → 技能积累）
- ✅ 产品链接可公开访问，无登录门槛，无断点
- ✅ 5 条真实小红书笔记数据，非 mock 占位符
- ✅ 观察视角框架清晰，逻辑自洽
- ✅ 差异化定位可说清楚（竞争对手不是飞书，而是"什么都不记"）
- ✅ 技术路径透明，可解释为什么不接真实 API
### 6.2 未验证假设（需真实用户数据才能判断）
- ❓ **低门槛能否真正改变记录行为**  
  这是产品最核心的假设：门槛足够低时，目标用户会不会真的随手记一句话。  
  目前没有用户使用数据支持，仅凭逻辑推断。

- ❓ **宠物机制能否支撑长期使用习惯**  
  游戏化机制对短期行为改变有一定效果，但能否转化为真正的长期习惯，研究结论是混合的。  
  Duolingo 的案例显示，部分用户会为维持连续天数而使用，而非真正在学习。  
  薯光是否会出现类似的"喂宠物但没有真实观察"的情况，尚未验证。

- ❓ **技能命名是否真正反映了用户的职业认同**  
  "评论区猎手"这个称号是否会让风控从业者感到被认可，还是感到轻浮？  
  需要真实用户测试。

- ❓ **模式卡的触发频率和模式命名质量能否达到预期**  
  当前模式卡内容为预置，真实 LLM 生成的模式名是否能达到"一句能被记住的命名"的质量，需要实际测试。
### 6.3 已知局限（设计阶段即有意识的取舍）
- **AI 分析为预置逻辑**  
  Demo 阶段不支持任意链接的实时解析。这是**主动决策**，为保证演示稳定性和规避 API 风险。真实产品版本需接入 LLM API。

- **数据不持久化**  
  刷新页面后记录消失。无账号系统，无云端同步。  
  这是技术架构的主动取舍，在 48 小时 Demo 阶段是正确决策，但作为真实产品需要完整的数据层。

- **Community 为静态展示**  
  当前不支持真实多用户交互。社区功能是对未来形态的展示，非当前可用功能。

- **单一视角视角框架尚未验证**  
  五个观察视角是基于对内容从业者职业逻辑的推断设计，未经真实用户调研验证是否完整、是否合理。

## 七、技术路径说明
| 层 | 工具 | 选择理由 |
|----|------|---------|
| 前端生成 | Lovable | AI 驱动，自然语言 prompt 直接生成 React 应用；48 小时内可交付可部署 Demo |
| 部署 | Lovable 自动部署 | 一键生成公开链接，无需服务器配置 |
| 代码托管 | GitHub | 版本管理，支持评审查阅源码 |
| AI 分析 | 预置逻辑（Demo 阶段） | 规避现场 API 失败风险；5 条真实笔记数据保证内容真实性 |
| 数据层 | 浏览器内存态 | 无后端无数据库；48 小时内最稳定可控的架构 |

**为什么不接真实 AI**（标准回答）：  
Demo 阶段采用预置数据，是为了保证演示稳定性。一个在现场崩掉的 Demo，比一个使用预置数据的 Demo 差得多。真实产品版本将接入 LLM API 实现实时分析。

## 八、下一步迭代路径（真实产品版本）

- 接入 LLM API，支持任意笔记链接的实时内容解析与结构化
- 用户账号系统与云端数据同步

- 多人使用时的团队技能分布可视化
